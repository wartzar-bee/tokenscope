Claude Code output token cost

The model writing code — generating replies, producing output — accounts for only ~15% of total spend in measured Claude Code sessions. The other 85% is context re-sending. Here's why, and when it changes.

The 60/25/15 split (measured, n=66)

From the n=66 benchmark, pooled across all 66 sessions:

Spend categoryShareDescription
Cache read (re-sent context)60%Accumulated context re-sent every turn
Cache write (new context)25%Context entering cache for the first time
Output15%Tokens the model generated — code, explanations
Fresh input~0%Uncached prompt tokens
The counter-intuitive result: the model writing code — the thing most users think of as "what I'm paying for" — is the smallest major line item on the bill.

Why output is a small fraction in long sessions

Output tokens are priced higher than input/cache rates — but output volume is much smaller than context volume in agentic coding sessions. The math:

  • A typical model reply: 100–500 tokens of code or explanation per turn.
  • At 29 turns (median), total output: ~3,000–15,000 tokens per session.
  • Context re-sent per turn (median 44,900 tokens) × 29 turns = ~1.3M tokens of context re-send events over the session.

Even with output priced 5–10× higher per token than cache-read, the volume difference (1.3M vs 15k tokens) means cache-read dominates the bill. Output contributes more per token but contributes fewer tokens.

When output cost is a larger fraction

The 15% figure is for the pooled dataset, dominated by longer sessions. The output fraction varies by session type:

Session typeOutput fraction (rough estimate)Why
Very short (<10 turns, small context)30–50%Few context re-sends; output becomes larger fraction of total
Typical (20–50 turns, ~50k context)10–20%Moderate context re-send volume
Long (100+ turns, 200k+ context)5–10%Large context re-sends dwarf output volume
Extreme (1,270 turns, 998k context)<5%Context re-send volume is enormous relative to output

The extreme 1,278-turn session had 66% of cost from cache-read alone — the model's code output was a small sliver of that bill. Full details in the anatomy study.

What this means for cost reduction

If output is 15% of spend, then actions that reduce only output (e.g. asking for shorter responses) address a small fraction of the bill. The much larger levers are the ones that reduce context re-sending:

  1. Keep context small. Don't open files that aren't needed; minimize verbose tool outputs.
  2. Compact or restart. /compact shrinks the accumulated context; a new session resets it to zero. Both reduce what's re-sent on subsequent turns.
  3. Start focused sessions. A session with a narrow scope stays smaller (fewer files, fewer tool results) than an open-ended explore-everything session.

See the full cost reduction guide for a prioritized checklist. Output optimization is worth doing — but it's downstream of context management.

FAQ

If output is more expensive per token, why does it cost less than input?

Per-token output rates are typically 5× or more higher than input rates. But in agentic coding, the context (input) volume is enormous — 44,900 tokens re-sent 29 times in the median session. The output volume is much smaller (typically 100–500 tokens per turn). Volume × rate = output loses on volume even though it wins on rate.

Does asking for shorter responses significantly reduce my bill?

It reduces the 15% output slice, and shorter replies also marginally reduce context growth (shorter prior messages). But for a long session where cache-read is 60–70% of spend, halving output length reduces total bill by ~7%. Compacting or restarting has much larger impact.

What counts as output tokens in Claude Code?

Everything the model generates in response to each turn: code it writes, explanations, tool call arguments, reasoning text (if thinking is enabled). These are counted by the API as output_tokens in the usage object for each request. tokenscope reads these from the session logs and applies the documented output rate.
