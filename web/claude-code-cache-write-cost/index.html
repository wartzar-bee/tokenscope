Claude Code cache write cost

Cache writes are the one-time cost of writing new context into the prompt cache — paid at 1.25× or 2× the input rate. They're more expensive than reads, but it's an investment: after the write, re-reads cost just 0.1× the input rate.

What triggers a cache write

Anthropic's prompt cache stores context at stable token boundaries. A cache write happens when new tokens are added to the cache for the first time — typically:

  • Opening a file. The file's content is added to the context. First time this exact content appears at this position → cache write.
  • Tool output arriving. A command result or search output is added to the context for the first time.
  • The initial system prompt. Claude Code's system prompt and tool definitions are written to cache at the start of a session.

Once a block is in the cache, subsequent turns that include it pay the read rate (0.1×) instead of the write rate (1.25× or 2×). The write is a one-time cost; the read is paid on every turn that includes that block.

The two cache write rates

Cache typeRateTTLWhen used
Standard1.25× input rate5 minutesDefault; short-lived sessions

Important: verify current rates at anthropic.com/pricing. Rates can change. tokenscope applies the documented rates at measurement time.

The extended cache costs more per write but protects against re-writes in slow sessions — where a long pause between turns would otherwise expire the 5-minute cache, forcing the context to be re-written on the next turn.

Cache write as 25% of session spend

From the n=66 benchmark, pooled across all sessions:

BucketPooled share
Cache read (re-sent context)60%
Cache write (new context → cache)25%
Output15%
Fresh input~0%

Cache-write is a significant fraction of spend, but it's the investment that enables the cheap re-reads. In a 60-turn session, writing 50k tokens to cache at 1.25× once, then reading those 50k tokens 60 times at 0.1×, the math is:

  • Write cost: 50,000 × 1.25 = 62,500 token-equivalents
  • Read cost: 50,000 × 60 × 0.1 = 300,000 token-equivalents

The write is 17% of the total — roughly the 25% benchmark figure, which makes sense given that longer sessions have proportionally more reads vs the initial write.

The break-even calculation

A cache write at 1.25× is worth it if you'll re-read that context more than 12.5 times (the write-vs-read break-even: 1.25 / 0.1 = 12.5). For the extended cache (2×), the break-even is 20 re-reads.

In practice, any Claude Code session longer than ~15–20 turns on the same stable context has already broken even on the cache investment. The benchmark median is 29 turns — well above the 5-minute cache break-even. Cache writes are almost always net-positive for agentic coding sessions.

When cache writes are wasteful

Cache writes become expensive relative to their value when:

  • The context expires before being re-read enough. If a long pause between turns causes the 5-minute cache to expire, the context is re-written on the next turn (another write at 1.25×) — but it may only be re-read 2–3 times before another expiry. Below the break-even, the write cost is net-negative vs paying fresh input.
  • Context is written then not re-read. If a file is opened, the context is written at 1.25×, but the session ends shortly after without many subsequent turns, the write cost isn't recovered through re-reads.

FAQ

Why does cache write cost more than the regular input rate?

Because Anthropic needs to store and index the context on their infrastructure to serve it cheaply on subsequent reads. The higher write rate covers that storage/indexing cost. The pay-off is the 0.1× re-read rate on subsequent turns.

Can I reduce cache write costs?

Somewhat. Keeping context stable (not restructuring it frequently) reduces re-writes. Avoiding opening files that aren't needed for the current turn avoids unnecessary writes. But cache-write at 25% of session spend is an expected cost of agentic coding — it's the investment that makes the 60% cache-read cost affordable.

What's the difference between cache_creation_input_tokens and cache_read_input_tokens?

These are the raw fields in Anthropic's API usage object for each call. cache_creation_input_tokens is the count of tokens written to cache this turn (charged at 1.25×–2×). cache_read_input_tokens is the count of tokens served from cache this turn (charged at 0.1×). tokenscope reads both from your session logs and uses them to compute the exact spend split.
