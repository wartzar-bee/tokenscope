Why long Claude Code sessions cost so much

A 1,270-turn session cost $1,278. The median 29-turn session cost $4.08. That's 44× more turns but 313× the cost. Here's the mechanic that makes the relationship super-linear.

The compounding effect: turns × context

Every turn in a Claude Code session re-sends the full accumulated context to the model. Early in a session, that context is small — a few thousand tokens of system prompt and the first exchange. As the session progresses:

  • Each file the model reads is added to the context.
  • Each tool result (command output, search result) is added.
  • Each reply from the model is added.

The context grows monotonically. And once it's large, every subsequent turn pays to re-send it in full — at the cache-read rate of 0.1× input price.

The key formula: cache_read_cost ≈ Σ(context_size_at_turn_t × cache_read_rate)
This is a partial sum of a growing sequence — not linear in turns, not linear in peak context, but in the product of the two.

Example: if context grows linearly from 0 to 200k tokens over 100 turns, the total context re-sent is roughly the area under that curve — approximately 100k × 100 turns = 10M tokens worth of cache-read cost. If the same task is split into two 50-turn sessions each reaching 100k peak, the total is roughly 50k × 50 turns × 2 = 5M — half the cost, for the same output.

Real data: how cost concentrates in long sessions

From the n=66 benchmark, the pooled spend split is:

BucketPooled shareNotes

Cache write25%One-time cost per unique context block

The pooled numbers are dominated by long sessions. The 66-session total of $2,650.90 included one session that alone cost approximately $1,278 — nearly half the total spend for just one session out of 66. That's the hallmark of super-linear cost growth: a small number of long sessions account for a disproportionate fraction of total spend.

The $1,278 session in detail: 1,270 turns / ~998k peak context / 66% of cost from cache-read alone. Read the full breakdown in the anatomy study.

Where it feels fast vs where it gets expensive

Agentic coding sessions have a characteristic shape:

  1. Early turns (1–20): Context is small. Each turn is fast to process and cheap. The model is reading initial files, setting up context.
  2. Mid session (20–60 turns): Context is growing. Each turn costs more as the accumulated read/write/tool history grows. The session might be making good progress.
  3. Late session (60+ turns): Context can be hundreds of thousands of tokens. Even a short model reply re-sends all of that. Cost per turn is significantly higher than early turns. This is where cost spikes become surprising.

The median session in the benchmark data (29 turns, $4.08) hits a peak context of ~44,900 tokens — well before the expensive late-session territory. The 90th percentile (67 turns, $11.42) reaches ~86,100 tokens. The extreme session reached ~998,000 tokens and ran for 1,270 turns — every late turn was paying to re-send nearly 1M tokens of context.

What to do about it

The most effective interventions target the context the model carries, not the number of turns per se (since turns themselves are often necessary):

ActionEffectWhen to use
/compactReplaces accumulated context with a shorter summary; reduces what's re-sent next turnBefore context grows very large; when you're switching to a new subtask within the session
Start a fresh sessionContext resets to zero; next turn sends only the initial system contextWhen moving to a different task, file, or code area
Avoid large file reads earlyKeeps context smaller in the growth phase; lower cost per subsequent turnWhen you don't actually need a large file for the current task
Close unnecessary tool resultsVerbose command output can add tens of thousands of tokens to the contextAfter a large command output is no longer relevant

FAQ

Does cost scale linearly with the number of turns?

No — it's super-linear. Cost grows roughly as the product of turns and context size. If context grows as the session runs (which it typically does), later turns pay more per turn than early ones. The 1,270-turn session was 44× more turns than the median 29-turn session but cost 313× more.

Is a long session always bad?

Not if the task genuinely requires it — complex refactors, multi-file analysis. The issue is unintentional length: sessions that run long because context wasn't managed, or because the task scope wasn't broken down. The cost of a well-focused 200-turn session may be entirely appropriate; the cost of a 200-turn session doing 20 unrelated tasks in sequence is mostly waste.

What's the practical threshold where a session starts getting expensive?

There's no universal threshold — it depends on the model's per-token rates and how much context has accumulated. A rough guide: once your session context grows past 100k tokens and you're on turn 50+, you're in the territory where the per-turn cost is a meaningful fraction of a dollar. tokenscope shows you the per-turn curve so you can see exactly when your sessions cross that zone.
