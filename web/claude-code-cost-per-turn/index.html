Claude Code cost per turn

Each turn in a Claude Code session isn't priced just on the new message. It's priced on everything the model has to carry — the whole accumulated context — re-sent from scratch every time you ask a question.

Why turns get more expensive as a session runs longer

LLMs are stateless. The client sends the full conversation — your messages, every file the model has read, every tool result, every prior reply — with each API request. Early in a session that payload is small. Later it can be hundreds of thousands of tokens.

The pricing for each turn breaks into three parts:

ComponentRateWhat contributes
Cache read0.1× input priceEverything already in the cache, re-sent this turn. Grows with every turn.
Cache write1.25–2× input priceNew context entering the cache this turn (a new file, a large tool result). One-time per unique context.
OutputOutput priceTokens the model generated — code, explanations. Usually the smallest component on later turns.
The counter-intuitive part: a turn where the model writes just two lines of code can cost more than an early turn where it read a large file — because the later turn re-sends a context that has since grown to hundreds of thousands of tokens.

For the extreme 1,270-turn session: the average cost per turn was roughly $1.01, but that masks the progression — early turns were cheap, while later turns carrying ~998k tokens of context cost significantly more each. The full turn-by-turn breakdown is in the anatomy study.

Pooled across all 66 sessions, 60% of total spend was cache-read — re-sending accumulated context — versus 15% on output tokens (what the model actually wrote).

The compounding effect: turns × context

The cost of a session grows roughly as:

total_cost ≈ Σ(context_size_at_turn_t × cache_read_rate) + cache_writes + outputs

Because context grows monotonically through a session (under normal usage), later turns are systematically more expensive than earlier ones. This is the quadratic-ish growth that makes long sessions expensive disproportionately:

  • A 10-turn session with 50k context peak might cost $1–2.
  • A 100-turn session with 200k context peak doesn't cost 10× more — it can cost 40–50× more, because both the context size and the number of turns it's re-sent at have grown.

This is the core reason the long session cost page treats session length as the primary cost driver.

How to reduce per-turn cost

The main lever is keeping the context the model carries small. Two approaches:

  1. Use /compact proactively. Compacting replaces the accumulated context with a shorter summary. The next turn re-sends the summary, not the full history. When to use /compact explains the trade-off.
  2. Start a fresh session for a new task. A new session starts with a small context. Moving to a fresh session after completing a significant subtask avoids carrying all that previous context into the next one.

FAQ

Does every turn cost the same?

No. Each turn costs more than the previous one (in a growing session), because the context re-sent this turn includes everything from all prior turns. Early turns are cheap; late turns in a long session can be much more expensive.

Why is output such a small part of the bill?

Measured data shows output is ~15% of pooled spend across 66 sessions. Output tokens are only the text the model generates in that turn. The context — everything the model reads before it writes — is typically much larger, even discounted at 0.1× via caching.

Can I see the cost of each individual turn?

Yes. Running npx @wartzar-bee/tokenscope shows a per-turn context-growth curve and the cost attribution for each turn in your session.
