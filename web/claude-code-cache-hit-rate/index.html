Claude Code cache hit rate

Cache efficiency tells you how much of your accumulated context is being re-read from cache versus rewritten from scratch. Measured across 66 real sessions: the median is 83%, the 90th percentile is 94%.

What cache efficiency measures

Every turn in a Claude Code session sends some tokens that were already in the cache (cache read) and potentially some new tokens entering the cache for the first time (cache write). Cache efficiency is the fraction of cached context that is reused rather than rewritten:

cache_efficiency = cache_read_tokens / (cache_read_tokens + cache_write_tokens)

A session with 100% efficiency means every cached token is read from an existing cache entry — nothing is being rewritten. In practice, efficiency rises as a session progresses, because early turns write new context and later turns mostly re-read it.

The pooled rate (98%) is higher than the per-session median (83%) because cost is concentrated in a few long sessions, and long sessions have much higher efficiency — they write context once and then re-read it hundreds of times.

Note: cache efficiency is a different metric from the cache-read fraction of spend. Even a 98%-efficient session spends 60% of its budget on cache reads — because the accumulated context is large and re-sent many times.

What drives cache efficiency

Efficiency goes up when:

  • Sessions run longer. More turns means more opportunities to re-read previously written context before it expires.
  • The stable prefix is large. Claude Code caches at stable token boundaries. A large, stable system prompt and tool definitions sit at the top of every call and accumulate reads quickly.
  • Turns happen quickly. The 5-minute TTL (short) and 1-hour TTL (extended) mean slow back-and-forth pauses may cause cache expiry, forcing a re-write.

Efficiency goes down when:

  • Sessions are very short. Few turns means few reads per write — the efficiency ratio stays low.
  • Long pauses between turns. If the cache expires, the context is rewritten on the next turn at the write rate (1.25× or 2×) instead of the read rate (0.1×).
  • Prompt structure changes frequently. Cache entries are tied to specific token boundaries. Restructuring the prompt mid-session (e.g. changing tool definitions) can invalidate cache entries, forcing re-writes.

Cache efficiency vs cache-read spend

High cache efficiency is good (you're reusing context, not rewriting it), but it doesn't mean your costs are low. A session with 98% cache efficiency but 500k tokens of accumulated context is still paying to re-send those 500k tokens every turn — at the 0.1× read rate, which still adds up on a 100-turn session.

The cache cost explainer covers how even the discounted read rate becomes the largest cost line on long sessions.

The two metrics to watch are:

  1. Cache efficiency — are you reusing vs rewriting? (Higher is better.)
  2. Peak context size — how large is the context being re-sent? (Smaller is cheaper per turn.)

FAQ

Is 83% cache efficiency good?

Yes — for a typical Claude Code session length, 83% is normal. It means most of the context is being served from cache rather than rewritten each turn. The practical range from 66 sessions is 69% (p10) to 94% (p90). Very low efficiency (below 50%) usually indicates short sessions, slow interaction causing TTL expiry, or significant prompt restructuring.

What's the difference between cache efficiency and cache hit rate?

They measure the same thing: how much of the cached context is served from an existing cache entry (read) versus written fresh (write). The formula above (cache_read / (cache_read + cache_write)) is what tokenscope calls cache efficiency. Some tools call this the cache hit rate. The Anthropic API returns cache_read_input_tokens and cache_creation_input_tokens separately in usage objects.

Can I improve my cache efficiency?

Somewhat. The main knobs are: (1) keep sessions active (avoid long idle pauses that expire the TTL), (2) don't restructure the prompt frequently, (3) run longer sessions on a focused task. But beyond those, efficiency is mostly a function of session length — the longer a session, the higher efficiency naturally becomes.
